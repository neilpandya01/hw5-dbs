# Sky Hunt

A plane-spotting game. Real planes flying near you show up on a map; catch them before they leave your 5-mile range (but not over an airport) and collect every airline and aircraft type. Flows are in `flows.md`; how data moves through the system is in `docs/data-flow.md`.

This is Assignment 5 (Live Data System) for Design, Build, Ship: a Supabase Edge Function, called every 30 seconds by Supabase Cron, fetches planes near active players (adsb.fi, one zone every 2 s; adsb.lol as a 30-second fallback), saves only what changed to Supabase, and Supabase Realtime pushes each zone's update to the page as one message. Everything runs on Vercel, Supabase, and Clerk (no Railway), within the free plans: the app limits itself per day (`docs/usage-limits.md`).

## Stack and rules
- Next.js 16 + Tailwind CSS 4, Clerk for sign-in, Supabase for the database, Realtime, and the worker (an Edge Function run by Supabase Cron). The page deploys on Vercel.
- The worker lives in `supabase/functions/worker/` (Deno on Supabase: `index.ts` is the entry, the logic is plain JavaScript in `src/` so Node can test it; `package.json` there only marks it as ES modules for the tests). The whole `supabase/` folder is excluded in `tsconfig.json` and `eslint.config.mjs` so the Next.js build doesn't check it. `supabase/config.toml` turns off JWT checks for it; it checks an `x-cron-secret` header instead.
- Ask before adding npm packages beyond Clerk, Supabase, Leaflet (the map), and Playwright.
- Keys (never committed, never read by the agent):
  - `.env.local` for the page: `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Only publishable keys reach the browser.
  - The worker's keys live only on Supabase: `SUPABASE_URL` and the secret key are provided to Edge Functions automatically; `CRON_SECRET` is an Edge Function secret, and the same value is in Vault (`sky_hunt_cron_secret`) next to the function's URL (`sky_hunt_worker_url`) so Cron can call it. The secret key skips row-level security; it never goes in the page or in code.
- Check with `npm run build`, `npm run lint`, and `npm run test:worker` before committing.
- Running locally: `npm run dev` (the page, localhost:3000). There is no local worker: the deployed one (Cron, every 30 s) serves everyone, including localhost, since they share the Supabase project. Never run a second copy; it would spend the shared daily limits twice as fast.

## Data (Supabase)
How data moves and the freshness states are in `docs/data-flow.md`; every usage limit and the reason for it in `docs/usage-limits.md`. The schema, policies, and functions are in `supabase/migrations/`. `user_id` is the Clerk user ID (`auth.jwt()->>'sub'`).

- `hunters`: one row per person: `onboarded`, `lat`/`lon` rounded to 2 decimals (about 1 km), `location_at`, `last_active_at`, `play_day`/`play_seconds` (today's Radar time). Own row only, and people may only write `onboarded`, `lat`, `lon`, `location_at` (column grants). `touch_hunter()` (security definer) stamps `last_active_at` with the database's clock and adds the time since the last check-in (max 30 s, nothing after a minute's gap) to today's Radar time (capped at 2 h). It returns the seconds left before your zone is slowed (0 = slowed).
- `sightings`: written only by the worker; keyed by `(cell, hex)`. `kind` is `commercial` | `private` | `unknown`; airline (ICAO, IATA, name), type (code, name), rarity, position, altitude, `heading` (direction of travel), `airport` (the no-catch zone it's in, if any), `seen_at` (when it was pinged). Signed-in people can read. **Not** in Realtime (one message per plane was too many); the page loads it, and `catch_plane()` checks it.
- `frames`: one row per zone (`cell`), overwritten by each update with changes: `planes` (sightings rows that changed), `removed` (hexes that left), `at`, `seq`, `pace` (`fast` | `normal` | `slow`: how often this zone is being updated). Written only by the worker. Signed-in people can read. In Realtime: one message per update per viewer.
- `runs`: one row per worker call: `ok`, `mode` (`fast` | `normal` | `slow` | `paused` | `idle`), cells, `ticks`, requests (`fi_requests`, `lol_requests`), `requests_24h` (adsb.lol) and `daily_budget` (500), `fi_requests_24h`, upserted, deleted, `rows_changed`, `messages_est`/`bytes_est` and `messages_24h`/`bytes_24h` (the worker's own Realtime meter), `resume_at`, `source` (which source answered last), `error` (every problem, including recovered ones; `ok` says whether every zone asked about got an answer). `worker_usage()` (secret key only) sums the last 24 h for the worker. Signed-in people can read. In Realtime (the page listens for inserts).
- `catches`: own rows only, and only created by `catch_plane(cell, hex, lat, lon)`, which saves the caller's rounded location and marks them active, then checks at the plane's last ping: commercial, under 90 s old, within 5.5 miles of the rounded location, not in an airport zone, not already caught today (same aircraft once per UTC day). Errors are codes (`OUT_OF_RANGE`, `STALE`, …) that `RadarView` explains.

Location privacy: the exact position stays in the browser's memory. Only coordinates rounded to 2 decimals are saved or sent anywhere; the saved copy updates after moving about 2 km, at most once a minute.

## The worker (`supabase/functions/worker/`)
- `index.ts`: the Edge Function. Checks `x-cron-secret`, then runs one call (about 20 s) and answers with its `runs` row. Each call starts from nothing: `loadState()` (in `src/run.js`) reads `worker_usage()` (24 h of requests per source, estimated messages and bytes, recent 429s) and the saved planes; if that fails the call makes no requests and is recorded as failed.
- Scheduling: `supabase/migrations/20261029000000_worker_cron.sql` (pg_cron + pg_net): `sky-hunt-worker` every 30 s (pg_net timeout 29 s, set in `20261030010000_fast_updates_and_limits.sql`), plus hourly pruning of `runs` older than 7 days and of Cron's own history. `src/db.ts` is the only file that talks to Supabase (`npm:` import, Deno only).
- `src/run.js`: one call: active hunters (last minute, with today's `play_seconds`) → zones (grid cells, `src/cells.js`, 0.25°; the page's `src/lib/cells.ts` must match), busiest first, with how many people watch each and how many are under 2 h today (`fastViewers`) → pace from `src/limits.js` → **fast**: adsb.fi, one zone per 2 s tick (ticks at 0, 2 … 20 s: 11 of them; up to 8 zones with `fastViewers` taking turns; zones where everyone is past 2 h get one odd tick each per call), or **normal/slow/paused**: one pass over up to 4 zones, 1.1 s apart, adsb.fi if available, else adsb.lol (pass when the fast allowance is used, adsb.fi refused in the last 5 min, it hit 12,000 today, or every active person is past 2 h). If adsb.fi stops answering mid-call, the rest of the call is a pass. For each answer, `src/changes.js` picks what changed; it's saved to `sightings` and, if anything changed, written as the zone's one `frames` row. Zones nobody's in are cleared first (no message). Then a `runs` row with the usage estimate, and one log line.
- `src/limits.js`: the free plan's daily share (monthly ÷ 30: 66,666 Realtime messages, about 167 MB egress). Fast under 50% of it (estimated over 24 h), 30-second updates to 90%, paused beyond. adsb.fi: 12,000 a day. Person: 2 h of fast updates a day, then 30-second updates (counted in the database, applied by the worker).
- `src/source.js`: two flight sources in the same format (`ac`, `now` in ms): adsb.fi v3 (first; 1 request/s per IP, errors can earn a temporary ban) and adsb.lol (fallback). Supabase's Edge Functions share outgoing IPs with other projects, so either can refuse (429) even when we've used little. A source that answers 429 is skipped for 5 minutes (found again from `runs.error`, `"<source> refused"`). A fetch times out after 4 s.
- `src/budget.js`: adsb.lol's budget, 500 requests per rolling 24 h. Under 75%: every 30 s. 75–90%: every 60 s (a call skips its request if the last adsb.lol one was under 55 s ago, and keeps its planes). 90%+: no adsb.lol requests (with an estimated `resume_at`). Only adsb.lol requests count.
- `src/classify.js`: commercial = airline-style callsign + an airline in `data/airlines.json` + an airliner type in `src/aircraft.js` (which also sets rarity). Tail-number callsigns and airline codes on non-airliners (NetJets) are private; no callsign/type, military, or unrecognized is unknown. Also marks planes in airport zones (`data/airports.json`).
- `data/airports.json` and `data/airlines.json` (imported as JSON, so they're bundled with the function) are generated by `scripts/build-airports.mjs` and `scripts/build-airlines.mjs` (sources and commands at the top of each).
- `test/` (`npm run test:worker`): `node --test` on a saved response (`test/fixtures/chicago.json`), an in-memory stand-in for Supabase, and a fake clock: fast ticks every 2 s and zones taking turns, only changes saved and bundled, leavers removed, the usage meter, the 50%/90% limits, the 4-zone pass, adsb.fi failing over to adsb.lol, adsb.lol's budget modes, both refusing, calls that rebuild their state from the database (as each Cron call does), and both sources' formats.

## Where things are (page)
- `src/lib/store.ts`: the only data layer for a person's own data (hunter row and catches). `useStore()` is null until it loads. Saves resolve false (and set `save-failed`) unless a row really changed. `catchPlane()` rounds your position before calling `catch_plane()` (which saves it), then updates the page's saved location to match, so the page and worker agree on your grid square. Failed loads and saves keep a technical `problem`, logged to the console and shown in `StorageBanner` only in development.
- `src/lib/supabase.ts`: the one browser client; sends the Clerk session token (set by `AccountSync`), which Realtime uses too. Publishable key only. `describeToken()` reports only the token's `role` and issuer, for the permission-error message.
- If loading fails with `permission denied` (42501), Supabase saw the request as signed out: the Clerk app's Supabase integration must be on (it adds `role: authenticated`), and Supabase's third-party auth must list this Clerk app's domain. Never fix it by granting access to `anon`.
- `src/lib/flights.ts`: `useFlights(cell)` (null = don't listen): loads the zone's planes (`sightings`) and the latest run, then listens with Realtime to `frames` (insert/update filtered to the zone: apply `planes`, drop `removed`, note `frameAt` for "updated X ago") and `runs` inserts; reloads on (re)subscribe and on returning to the tab. After a minute hidden it closes its channel (every message to an unwatched tab still counts) and reconnects on return. Each subscription uses a unique topic (the client hands back an existing same-named channel, even one being torn down, which silently killed updates). It reports `connection` (connecting, live, reconnecting), reconnects 3 s after a drop, and if nothing arrives for 75 s reloads and reconnects. `useNow()` ticks the clock (0 until mounted).
- `AccountSync`'s token source always hands over a Clerk token with 45+ seconds left (Realtime refreshes it every 25 s and closes the channel, without resubscribing, if it expires first).
- `src/lib/nearby.ts`: what to show (out to 15 mi; at most 12 inside the 5-mile circle and 15 outside, closest first; positions older than 2 min hidden), `catchBlock()` (why a plane can't be caught), `feedState()` (from the run, the zone's latest update and its `pace`, and the connection: loading, down, limit, connecting, starting, stale, fresh with `pace` fast/normal/slow; exactly one applies, in that order), names ("Private plane", "Unknown aircraft").
- `src/lib/heartbeat.ts`: while the radar is open and visible, `touch_hunter()` every 25 s; returns the fast Radar time left today. There's no timer on the page: at 0, `FeedStatus` gets `playedOut` and, when the zone's pace is `normal`, says "2 h played today, slower updates".
- `src/lib/location.ts`: `locateOnce()` for onboarding (15 s timeout); `useLiveLocation()` follows the position and saves the rounded copy when it changed enough (only the first fix has a time limit: a watch's later timeouts keep the last known position; "blocked" always shows); `problemMessage()` and `DEVICE_LOCATION_HELP` explain blocked or unavailable location (`LocationHelp.tsx` shows them).
- `src/lib/geo.ts`: rounding, distances, offsets, compass names, `CATCH_RANGE_MI` (5). `src/lib/airports.ts`: airport zones from `public/airports.json` (3 mi large, 2 mi medium). `src/lib/rarity.ts`, `src/lib/collection.ts`: tiers and points, and the Collection's grouping (each group carries its catches and total points; rows expand to list them). `src/lib/nearestPlace.ts`: "Near Chicago, Illinois" (BigDataCloud).
- `src/components/FlightMap.tsx`: the live map (Leaflet, browser only). You, your 5-mile circle, airport zones (codes from zoom 10 in, full name on hover or tap), and planes rotated to their direction with a short dashed line ahead of the nose; faded when they can't be caught. The line is part of the plane's icon (`.plane-trail`), not a separate map line: two separate layers drifted apart. Plane markers are kept and only touched when the plane moved, turned, or changed look (never just because the page re-rendered, which it does every second: rebuilding swallowed clicks). Updates wait while a zoom animation runs. Following re-centers only when you've moved visibly (24+ px), and airport zones are redrawn only when the visible set or label style changes. Per-map state (zooming, following) resets whenever the map is created. The selected plane is drawn bold in the accent color at the same size (`.plane-marker.is-selected` in `globals.css`), on top of others; its direction line stays grey. Every pick from the list bumps `frameRequest`, and if the plane isn't well inside the visible map, the map fits you and it (never zooming in). Never set `position` on `.plane-marker`: Leaflet needs its markers `position: absolute`, and overriding it laid the planes out one after another, away from their lines. Its card renders in `RadarView` directly below the map; a click on empty map calls `onMapClick`. Tiles: Esri's grey Canvas basemaps (no key). CARTO's tiles now require a key, and OpenStreetMap's own servers block apps that don't follow their policy, so don't switch to either.
- `src/components/PlaneCard.tsx`: only the airline (logo via `AirlineLogo.tsx`, from pics.avs.io by IATA code; the radar preloads logos for every airline on the map, and the code shows as a placeholder until the image is ready), aircraft type, and "Updated X ago", plus Catch or why not. `FeedStatus.tsx`: the freshness pill (loading, live with its pace, stale) and, instead of it, one banner when flight data is down or the day's limit is reached. The Radar credits adsb.fi and adsb.lol at the bottom (adsb.fi's terms require it).
- `src/components/Radar.tsx`: the simple radar drawing, only for onboarding's practice catch.
- `src/proxy.ts`: Clerk middleware; every route except `/sign-in` and `/sign-up` needs an account. (Clerk warns that `createRouteMatcher` is deprecated; it still works.) `AccountSync.tsx` loads data and hands Clerk's token to Supabase. `OnboardingGate.tsx` sends new people to `/welcome`.
- Routes: `/` Radar, `/collection`, `/welcome` (`?step=overview|location|tutorial`), `/sign-in`, `/sign-up`.

## How it behaves
- **Onboarding is required**, and so is location: overview, share location (no skip; blocked or failed location explains how to fix it; a failed save says so instead of moving on), and a practice catch (skippable). The practice plane cruises at 24,000 ft, about 450 mph, and moves every 10 to 15 seconds like real data.
- **Radar** follows your position while open, marks you active, and shows live planes, updated every few seconds (every 30 s once the day's fast allowance is used). Freshness is always visible; when flight data is down or the day's limit is reached, planes are hidden and a banner says to come back later. Each person gets 2 hours of 2-second updates a day; after that their zone updates every 30 s (unless someone else there is under 2 hours), with a brief note in the status line and no timer.
- **Catching** needs a commercial flight whose latest ping (under 90 s old) was inside your 5-mile circle and not over an airport. Private and unknown planes show but can't be caught.

## Next.js gotchas here
- Cache Components is on: pages you leave are hidden (React `<Activity>`), not unmounted. Don't leave buttons stuck busy; reset transient UI in a `useLayoutEffect` cleanup.
- Any client component reading the URL (`usePathname`, `useParams`, `useSearchParams`) must be inside `<Suspense>`, or the build fails.

## Style
- Colors come from tokens in `src/app/globals.css` (light and dark). Rarity always shows its name, never color alone. Every control has a label; everything works by keyboard, including planes on the radar.
